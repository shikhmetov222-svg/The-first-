# План этапа 2: мультиплеер через Supabase Realtime

Цель этапа: несколько игроков управляют **одной общей колонией**. Хост создаёт комнату, друзья входят по 6-значному коду. Каждый раунд игроки голосуют, какое действие сделать. Ресурсы, события и итог голосования одинаковы у всех.

Это план, кода пока нет. Вопросы к тебе — в разделе 8. Ответы на них могут что-то поменять в плане.

---

## Коротко о главных решениях

| Вопрос | Решение | Почему |
|---|---|---|
| Где правда об игре | В базе Supabase | Браузер игрока можно подделать, а базу нельзя |
| Кто считает раунд и голоса | Функции в базе (не хост) | Хост может схитрить или закрыть приложение |
| Как игроки узнают об изменениях | Supabase Realtime: подписка на изменения таблиц | Не нужно постоянно спрашивать сервер «что нового?» |
| Как игрок «входит» | Анонимный вход Supabase (Anonymous Sign-In) | Не нужен свой сервер и секретный токен бота |
| Чем подключаться к Supabase | Библиотека `supabase-js` через `<script>` с CDN, как Telegram SDK | Ничего не устанавливаем, сборщика нет, код остаётся чистым JS |
| Можно ли менять таблицы из браузера | Нельзя: только читать свою комнату | Так чужие ресурсы не изменить даже с ключом |

## 1. Схема базы данных

### Главная идея

**Одна строка в таблице `rooms` — это одна колония.** В ней лежат ресурсы, номер раунда и статус игры. Чтобы узнать «что сейчас в игре», достаточно прочитать эту строку. Чтобы показать игру, клиент тоже читает её.

### Таблицы

**`rooms` — комнаты (колонии)**

| Поле | Тип | Что значит |
|---|---|---|
| `id` | uuid | Внутренний номер комнаты |
| `code` | text, уникальный | 6 цифр для входа, например `482913` |
| `host_id` | uuid | Кто хост (id игрока из входа Supabase) |
| `status` | text | `lobby` (ждём игроков), `playing`, `won`, `lost` |
| `round` | int | Текущий раунд, 1…8 |
| `total_rounds` | int | Всего раундов (8) |
| `oxygen`, `water`, `food`, `energy`, `parts` | int | Ресурсы колонии |
| `round_ends_at` | timestamptz | Когда кончается время на голосование в этом раунде |
| `last_event` | text | Последнее случайное событие (для показа на экране) |
| `created_at`, `updated_at` | timestamptz | Когда создана и когда менялась |

**`players` — кто в какой комнате**

| Поле | Тип | Что значит |
|---|---|---|
| `room_id` | uuid → `rooms.id` | Комната |
| `user_id` | uuid | Игрок (id из входа Supabase) |
| `name` | text | Имя из Telegram или «Колонист» |
| `joined_at` | timestamptz | Когда вошёл |
| `left_at` | timestamptz, может быть пустым | Когда вышел сам (пусто — ещё в игре) |

Главный ключ — пара `(room_id, user_id)`: один игрок может быть в комнате только один раз.

**`votes` — голоса**

| Поле | Тип | Что значит |
|---|---|---|
| `room_id`, `round`, `user_id` | | Кто, где и в каком раунде голосовал |
| `choice` | text | За что, например `repair` или `skip` |

Главный ключ — `(room_id, round, user_id)`: один голос на игрока за раунд. Переголосовать можно, тогда голос заменяется.

**`room_log` — журнал колонии**

| Поле | Тип | Что значит |
|---|---|---|
| `id` | bigint | Номер записи по порядку |
| `room_id`, `round` | | Где и когда |
| `text` | text | Например «Раунд 3: утечка −3 воды. Решили: починить энергосистему» |
| `created_at` | timestamptz | Время записи |

### Почему ресурсы не в отдельной таблице

Ресурсов пять, и они всегда меняются вместе. Если держать их в строке комнаты, одно обновление строки меняет всё сразу. Тогда игроки никогда не увидят «половину раунда».

### Уборка

Старые комнаты (неактивные больше суток) удаляются раз в час через `pg_cron`. Голоса и журнал удаляются вместе с комнатой (`on delete cascade`).

## 2. Вход в игру

### Кто такой «игрок» для базы

При первом запуске клиент делает **анонимный вход** в Supabase (`signInAnonymously`). Supabase выдаёт игроку постоянный id (`user_id`) и «пропуск» (токен). Библиотека `supabase-js` сама сохраняет пропуск в памяти браузера (`localStorage`) и сама его продлевает.

Почему так:
- Не нужен свой сервер. Для настоящей проверки Telegram нужен секретный токен бота, а его нельзя класть в браузер.
- Правила доступа в базе (раздел 5) знают, кто именно делает запрос (`auth.uid()`).

Минус: имя из Telegram берётся «на слово» (`initDataUnsafe`). Подделать его может только сам игрок, и только у себя в игре. Для игры с друзьями это не страшно. Настоящая проверка через Telegram — вопрос 4 в разделе 8.

### Создание комнаты (хост)

1. Игрок нажимает «Создать колонию».
2. Клиент вызывает функцию базы `create_room(name)`.
3. База придумывает случайный 6-значный код (если такой уже занят — придумывает другой), создаёт комнату со стартовыми ресурсами и добавляет хоста в `players`.
4. Хост видит экран ожидания («лобби»): код крупно, кнопку «Поделиться» и список игроков.

### Вход по коду

1. Игрок нажимает «Войти по коду» и вводит 6 цифр.
2. Клиент вызывает `join_room(code, name)`.
3. База проверяет: комната есть, игроков меньше предела, игра ещё не закончена. Если что-то не так — понятная ошибка («Колония с таким кодом не найдена — проверь цифры»).
4. Игрок попадает в лобби. Когда хост нажмёт «Начать», игра пойдёт у всех.

Удобство: «Поделиться» отправляет ссылку `t.me/имя_бота/приложение?startapp=482913`. Друг открывает её, и код подставляется сам (Telegram передаёт его в `start_param`).

### Если игрок закрыл приложение

- **Пропуск остался в памяти телефона.** При следующем запуске клиент вызывает `my_room()`. База находит комнату, где игрок есть и игра не закончена, и игрок сразу возвращается на свой экран.
- **Игрок в комнате остаётся.** Закрыть приложение — не значит выйти. Выход только по кнопке «Покинуть колонию» (`leave_room`).
- **Игра без него не стоит.** Раунд закончится по таймеру, а голос отсутствующего просто не считается.
- **Хост закрыл приложение.** Ничего не ломается: раунды ведёт база (раздел 4). Если хост *вышел* по кнопке, хостом становится игрок, который вошёл раньше остальных.
- **Пропуск потерян** (очистили данные Telegram или зашли с другого телефона). Это будет уже «новый» игрок. Он может войти в ту же комнату по коду заново. Полностью эту проблему решает вход через Telegram — вопрос 4.

## 3. Синхронизация: что общее, а что только у тебя

### Общее — хранится в базе и приходит всем через Realtime

| Данные | Где лежит |
|---|---|
| Ресурсы, раунд, статус игры, время конца раунда | строка в `rooms` |
| Последнее событие | `rooms.last_event` и запись в `room_log` |
| Список игроков | `players` |
| Голоса текущего раунда | `votes` |
| Журнал колонии | `room_log` |

**Как это работает.** Клиент подписывается на изменения своей комнаты (Realtime → *Postgres Changes*, с фильтром `room_id = ...`). Когда что-то меняется, приходит сигнал, и клиент заново загружает состояние комнаты одним запросом `get_room(room_id)`.

Почему «сигнал + загрузить заново», а не собирать состояние из кусочков. Это проще и надёжнее: если сигнал потерялся (телефон уснул, пропал интернет), следующая загрузка всё равно покажет правильную картину. После переподключения клиент тоже один раз загружает всё заново.

### Только у игрока — считается в браузере, в базу не пишется

- **Какой экран открыт:** меню, лобби, игра, итог.
- **Обратный отсчёт таймера** («осталось 0:42»). Он считается из `round_ends_at`, и сервер не шлёт его каждую секунду.
- **Подсказки и вид кнопок:** кнопка «серая», «ты уже проголосовал», красный ⚠ при малом запасе.
- **Счёт голосов на экране** («2 за починку, 1 за пропуск»): считается из списка голосов.
- **Кто сейчас онлайн:** Realtime *Presence*, зелёная точка у имени. Это живой сигнал «я на связи», в базу он не пишется.
- **Вибрация, анимации, звуки.**

Ни одно число игры (ресурсы, итог голосования, событие) клиент **не считает сам**. Он только показывает то, что прислала база.

## 4. Кто запускает раунд и считает голоса

### Выбор: база данных (функции SQL)

Было два варианта:

| | Хост-клиент | База данных |
|---|---|---|
| Можно ли схитрить | Да: хост может прислать любые ресурсы или «подкрутить» событие | Нет: правила в базе, игрок их не видит и не меняет |
| Хост закрыл приложение | Игра встаёт | Игра идёт дальше |
| Два раунда сразу (двойной клик, плохая связь) | Возможно, если не делать сложную защиту | База блокирует строку комнаты, и раунд пройдёт ровно один раз |
| Сложность | Логика в JS, но нужна защита от всего перечисленного | Логика в SQL, зато защита встроенная |

**Выбрана база данных.** Главная причина: при хосте-клиенте честность игры зависит от одного телефона. При базе правила одни для всех, и подделать их нельзя.

### Как именно идёт раунд

В базе есть функция `resolve_round(room_id)`. Это «конец раунда», и вызывать напрямую её нельзя. Она:
1. Блокирует строку комнаты (`for update`): никто другой в эту секунду раунд не закончит.
2. Подсчитывает голоса. Побеждает действие с большинством голосов; что делать при ничьей — вопрос 2.
3. Применяет действие (например, починка: −1 запчасть, +3 энергии, если запчасти есть).
4. Делает обычный расход: −1 кислород, −1 вода, −1 еда.
5. Выбирает случайное событие (`random()` прямо в базе) и применяет его.
6. Пишет запись в журнал.
7. Проверяет поражение и победу. Если игра продолжается — раунд +1 и новый `round_ends_at`.

**Что запускает `resolve_round`.** Тут нет «главного» телефона:
- **Все проголосовали.** Последний голос в `cast_vote` сам вызывает `resolve_round`, и раунд заканчивается сразу.
- **Вышло время.** Когда таймер на экране дошёл до нуля, *любой* клиент вызывает `advance_round(room_id)`. База сама проверяет, что время действительно вышло (`now() >= round_ends_at`). Если нет — ничего не делает. Нажать «раньше времени» нельзя. Если позвали сразу трое, раунд всё равно пройдёт один раз: номер раунда сверяется под блокировкой.
- **Никого нет онлайн.** Тогда раунд просто ждёт. Первый вернувшийся игрок вызовет `advance_round`. Пропущенные раунды за один вызов не прокручиваются, иначе колония «умрёт», пока все спят (вопрос 3).

Почему не триггер. Триггер срабатывает при изменении строки, а «время вышло» — это не изменение. Поэтому для голосов — вызов из `cast_vote`, а для времени — проверка в `advance_round`.

### Список функций базы

| Функция | Кто вызывает | Что делает |
|---|---|---|
| `create_room(name)` | любой | Создать комнату, стать хостом |
| `join_room(code, name)` | любой | Войти по коду |
| `my_room()` | любой | Найти свою незаконченную комнату (возврат после закрытия) |
| `get_room(room_id)` | участник | Всё состояние комнаты одним ответом |
| `start_game(room_id)` | только хост | Начать игру из лобби |
| `cast_vote(room_id, round, choice)` | участник | Проголосовать (или переголосовать) |
| `advance_round(room_id)` | участник | «Время вышло?» — если да, закончить раунд |
| `leave_room(room_id)` | участник | Выйти; если вышел хост — передать роль |
| `restart_room(room_id)` | только хост | «Сыграть снова» той же компанией |
| `resolve_round(room_id)` | только другие функции | Конец раунда (см. выше) |

Все функции написаны на plpgsql, `security definer`, с `set search_path = ''`. Внутри каждая проверяет, кто вызывает (`auth.uid()`) и можно ли ему это. Ошибки — понятным текстом, например «Голосование в этом раунде уже закончилось».

## 5. Безопасность (Row Level Security)

**Публичный ключ (publishable key)** лежит в браузере, и его видит кто угодно. Поэтому защищает не ключ, а **правила в базе**.

### Правила

1. **RLS включён на всех четырёх таблицах.** Пока правила нет, таблица закрыта полностью.
2. **Только чтение и только своей комнаты.** Для каждой таблицы одно правило `SELECT`: строку видно, если ты участник этой комнаты.
   ```sql
   -- пример для rooms
   create policy "участник видит свою комнату" on public.rooms
     for select to authenticated
     using (public.is_room_member(id));
   ```
   `is_room_member` — небольшая функция: «есть ли `auth.uid()` в `players` этой комнаты». Она нужна, чтобы правило для `players` не ссылалось само на себя.
3. **Нет ни одного правила на `INSERT`, `UPDATE`, `DELETE`.** Значит, напрямую из браузера нельзя ничего добавить, изменить или удалить. Даже свою строку, даже с ключом.
4. **Все изменения — только через функции из раздела 4.** Функции проверяют правила игры и права.
5. **Права на функции.** Вызывать их может только вошедший игрок (роль `authenticated`), а не «прохожий» с одним ключом (`anon`). `resolve_round` не может вызвать никто снаружи.
   ```sql
   revoke execute on all functions in schema public from public, anon, authenticated;
   grant execute on function public.create_room(text) to authenticated;
   -- ...и так для каждой «внешней» функции
   ```
6. **Realtime тоже подчиняется RLS.** Подписка на `rooms` присылает изменения только тех строк, которые игроку разрешено видеть. Чужую комнату не подслушать.

### Что ещё защищено

- **Подбор кода.** Вариантов кода миллион. Комнаты живут недолго, а войти можно только в незаконченную. Если понадобится, добавим ограничение числа попыток входа.
- **Спам комнатами.** Один игрок может держать только одну незаконченную комнату. Старые комнаты удаляются сами.
- **Как проверим.** На этапе 1 реализации (раздел 7) прямо из консоли браузера с публичным ключом попробуем `update rooms set oxygen = 999`. Должен прийти отказ.

## 6. Что нужно сделать вручную

Это делаешь ты. По одному шагу; после каждого я скажу, что дальше.

1. **Создать проект Supabase.**
   - Зайти на https://supabase.com, нажать **New project**.
   - Название: `colony-mars`. Регион: **Central EU (Frankfurt)**.
   - Пароль базы придумать и сохранить у себя. В код он не попадёт.
2. **Включить анонимный вход.**
   - **Authentication → Sign In / Providers → Anonymous Sign-Ins** → включить.
3. **Скопировать два значения.**
   - **Project Settings → API Keys** (или кнопка **Connect**):
     - **Project URL** — вида `https://abcdefgh.supabase.co`;
     - **Publishable key** — начинается с `sb_publishable_...`. Если в проекте старые ключи — это `anon public`.
   - **НЕ копировать** ключи `service_role` и `sb_secret_...`. Они дают полный доступ к базе и в игру не должны попасть никогда.
4. **Прислать мне эти два значения.** Я положу их в `colony-mars/config.js`:
   ```js
   // Адрес проекта и ПУБЛИЧНЫЙ ключ Supabase.
   // Секретных ключей здесь нет и быть не должно.
   window.COLONY_CONFIG = {
     supabaseUrl: 'https://abcdefgh.supabase.co',
     supabaseKey: 'sb_publishable_...',
   };
   ```
   Публичный ключ можно хранить в репозитории: без правил из раздела 5 он ничего не даёт.
5. **Загрузить SQL в базу.** Я подготовлю файлы `colony-mars/sql/001_….sql` и проверю их на локальной базе. Дальше вариант зависит от твоего ответа на вопрос 7:
   - ты вставляешь файл в **SQL Editor** проекта и нажимаешь **Run**;
   - или я загружаю его сам через подключённый Supabase.
6. **В конце — проверить в Telegram с двух телефонов** (свой и друга).

## 7. Этапы реализации

Каждый этап заканчивается проверкой, которую можно сделать отдельно. Следующий начинаем, только когда прошла проверка предыдущего.

| № | Что делаем | Как проверить |
|---|---|---|
| 0 | Ручные шаги из раздела 6, файл `config.js` | Проект открывается в Supabase, в `config.js` нет слов `secret` и `service_role` |
| 1 | SQL: таблицы и RLS (пока без функций) | Из консоли браузера с публичным ключом не получается ни прочитать, ни изменить таблицы |
| 2 | Подключение: `supabase-js` с CDN, анонимный вход, надпись «На связи» | После перезагрузки страницы id игрока тот же (видно в DEV-строке внизу экрана) |
| 3 | Меню и лобби: `create_room`, `join_room`, `get_room` | Два окна браузера (обычное и «инкогнито»): одно создаёт, второе входит по коду, оба видят двоих игроков после обновления страницы |
| 4 | Realtime в лобби: список игроков обновляется сам + Presence (кто онлайн) | Второе окно входит — в первом игрок появляется без обновления; закрыл окно — точка погасла |
| 5 | Игра без голосования: `start_game`, таймер, `advance_round`, `resolve_round` | Один игрок: таймер дошёл до нуля → раунд +1, ресурсы изменились, событие в журнале. Повторный вызов `advance_round` раньше времени ничего не меняет |
| 6 | Голосование: `cast_vote`, досрочный конец раунда | Три окна: все проголосовали — раунд закончился сразу; итог одинаковый у всех трёх |
| 7 | Возврат и выход: `my_room`, `leave_room`, передача роли хоста | Закрыл вкладку посреди игры, открыл — снова в своей колонии. Хост вышел — хостом стал следующий |
| 8 | Конец игры: экран итога у всех, «Сыграть снова», уборка старых комнат | Довести игру до победы и до поражения; старая тестовая комната исчезает через сутки |
| 9 | Telegram: код из ссылки `startapp`, выкладка на хостинг, проверка с двух телефонов | Друг открывает ссылку — сразу попадает в лобби твоей колонии |

**Одиночная игра остаётся.** В меню будет «Играть одному» (нынешний `app.js`) и «Играть вместе» (новое). Файлы будут лежать раздельно, без сборщика, просто несколько тегов `<script>`:

```
colony-mars/
  index.html      + тег supabase-js с CDN и новые скрипты
  config.js       адрес и публичный ключ Supabase
  solo.js         одиночная игра (нынешний app.js, почти без изменений)
  net.js          всё общение с Supabase: вход, функции, подписки
  app.js          меню и экраны мультиплеера
  sql/            SQL-файлы по порядку: 001_tables.sql, 002_functions.sql, …
```

Про `supabase-js`. Это не установка пакета: один тег `<script>` с точной версией библиотеки, как уже подключён Telegram SDK. Писать общение с Realtime вручную (WebSocket, переподключения, продление пропуска) — сотни строк сложного кода. Библиотека делает это надёжно.

В `index.html` добавятся теги скриптов; `style.css` получит стили для меню, лобби и голосования.

## 8. Вопросы к тебе

Под каждым вопросом — что я сделаю, если ответа не будет.

1. **За что голосуем?** В одиночной игре действие одно — «Починить энергосистему». Голосовать «починить / не чинить» скучно. Предлагаю 3 варианта на раунд:
   - «Починить энергосистему»: −1 запчасть, +3 энергии;
   - «Запустить переработку воды»: −2 энергии, +2 воды;
   - «Включить теплицу»: −2 энергии, +2 еды.

   Так энергия наконец станет нужна. *По умолчанию: эти три варианта.*
2. **Ничья в голосовании или никто не проголосовал.** *По умолчанию: ничья — решает голос хоста, а если хост не голосовал — ничего не делаем. Никто не голосовал — ничего не делаем.*
3. **Время на раунд** и что делать, если все ушли. *По умолчанию: 60 секунд; если онлайн никого нет, раунд ждёт, пока кто-то вернётся.*
4. **Нужна ли настоящая проверка Telegram?** С ней имя нельзя подделать, а игрок не теряется при смене телефона. Но нужна Edge Function в Supabase и токен бота в секретах проекта: ещё один ручной шаг. *По умолчанию: на этапе 2 — анонимный вход, проверку Telegram добавим после, если понадобится.*
5. **Сколько игроков в комнате** и можно ли войти, когда игра уже идёт. *По умолчанию: от 1 до 6 игроков, войти можно и посреди игры.*
6. **Баланс.** С нынешними числами победа выпадает примерно в 1 игре из 300 (проверено на этапе 1). Менять ли числа для мультиплеера — например, старт 15 вместо 10? *По умолчанию: старт 15 кислорода, воды и еды, а одиночную игру не трогаю, пока не скажешь.*
7. **Какой проект Supabase.** Отдельный новый проект `colony-mars` или таблицы в уже существующем проекте CAPITAL? На бесплатном тарифе можно держать только 2 активных проекта. *По умолчанию: отдельный проект — так игры друг другу не мешают.* И как загружать SQL: ты вставляешь его в SQL Editor или я загружаю сам через подключённый Supabase? *По умолчанию: я сам, после твоего «да».*
8. **Хостинг.** Для CAPITAL кончились бесплатные кредиты Netlify, и он переехал на GitHub Pages. Выкладывать колонию тоже на GitHub Pages? Сейчас сайт публикует только CAPITAL и «Золотое число», поэтому придётся добавить одну строку в сборку сайта (`.github/workflows/pages.yml`): копировать папку `colony-mars`. *По умолчанию: да, по адресу `…github.io/The-first-/colony-mars/` после переноса в ветку `main`.*
